## Durable Persistence & Replay Fidelity

- [X] CHK001 Are the requirements explicit about what constitutes the durable persistence unit — per-agent vs per-agent-per-session — given the spec says "per-agent" (FR-016) but the data model joins on `agentId` + `sessionId`? [Consistency, Spec §FR-016 / data-model §Entity Table] <!-- Evaluator: Resolved — added FR-038 (keyed by agentId, segmented by sessionId) reconciling FR-016 with the data-model join key -->
- [X] CHK002 Is "durably persist" defined precisely enough (append-on-event, flush/durability guarantee at the time of write) to be testable, rather than relying on the undefined adjective "durable"? [Measurability, Spec §FR-016] <!-- Evaluator: Resolved — added FR-037 (per-event append-and-commit before forward; mirrors cost-ledger.jsonl) -->
- [X] CHK003 Do the requirements define what a "complete" persisted run is versus a "partial" one, so that graceful-degradation behavior has an unambiguous trigger condition? [Ambiguity, Spec §Edge Cases / data-model §C5] <!-- Evaluator: Resolved — added FR-042 (complete = ends with terminal stop + all lines parse; else partial) -->
- [X] CHK004 Are the four failure modes for a persisted log on replay (missing, partial, corrupt, truncated) each given a distinct expected outcome, or are they collapsed into one undifferentiated "render what is available"? [Completeness, Spec §FR-016 / plan §Error Handling] <!-- Evaluator: Resolved — added FR-042 (a/b/c/d distinct outcomes) + data-model §C5 expansion -->
- [X] CHK005 Is "renders what is available without erroring" stated as a measurable acceptance criterion (e.g., a corrupt/unparseable line is skipped and replay continues) rather than an aspiration? [Measurability, Spec §FR-016 / data-model §C5] <!-- Evaluator: Resolved — added SC-023 (feed malformed fixtures, assert no throw + expected prefix) -->
- [X] CHK006 Do the requirements specify that replay-on-reopen and replay-on-restart reconstruct the same transcript and structured view as the live render (replay fidelity / idempotency), or only that they "rebuild from the persisted stream"? [Completeness, Spec §SC-009 / FR-016] <!-- Evaluator: Resolved — added FR-039 (deterministic+idempotent; same views as live) + SC-022 -->
- [X] CHK007 Is idempotency of replay addressed — that re-opening or restarting multiple times does not duplicate, append to, or mutate the persisted log? [Completeness, Spec §FR-016] <!-- Evaluator: Resolved — FR-039 (replay is read-only over append-only log; N reopens don't mutate) + SC-022 -->
- [X] CHK008 Are requirements defined for log lifecycle and retention (when a persisted run record is created, rotated, or removed), given the spec mandates "no eviction" for in-memory entries but is silent on on-disk lifecycle? [Coverage, Spec §FR-010 / data-model §State Machines] <!-- Evaluator: Resolved — added FR-040 (on-disk append-only, retained for run life; no rotation/pruning within scale; consistent with FR-010/FR-031) -->
- [X] CHK009 Is the session-boundary behavior of the log defined — whether a new session appends to the same file or starts a new one, and how multiple sessions of one agent are distinguished on replay? [Completeness, data-model §Entity Table] <!-- Evaluator: Resolved — FR-038 (new session appends to same per-agent file; replay segments by sessionId) -->
- [X] CHK010 Do the requirements state whether the persisted stream or the rendered transcript is the source of truth for replay, given FR-016 uses "and/or" ("AgentEvent stream and/or rendered transcript")? [Ambiguity, Spec §FR-016 / Key Entities] <!-- Evaluator: Resolved — FR-016 amended: AgentEvent stream is the source of truth; transcript always re-derived (removed "and/or" ambiguity) -->
- [X] CHK011 Are storage-growth limits or an accepted-tradeoff threshold quantified, given persistence "grows storage" is acknowledged as a risk with no bound? [Measurability, Spec §Risks / plan §Risk Mitigation] <!-- Evaluator: Covered by spec.md §FR-031 (operating scale: hundreds–thousands events/run, 5–15 desks; revisit trigger beyond) reinforced by new FR-040 -->

## Event-Fold Correctness (Token Usage)

[Ambiguity, data-model §C7 / plan §HINT-003] <!-- Evaluator: Resolved — FR-036 states "set-not-sum" (sample REPLACES, never added) as a requirement; data-model §C7 now mirrors -->
- [X] CHK018 Is the "never decreases" invariant for token usage stated as a testable requirement, including the expected behavior if a non-monotonic (decreasing) sample is ever received? [Measurability, data-model §C7] <!-- Evaluator: Resolved — FR-036 (never decreases; decreasing sample clamped to last-known max) + SC-024 (testable fold over non-monotonic fixture) -->
- [X] CHK019 Do the requirements define how `usd: null` is handled in the projection (treated as "unpriced/unknown", never read as 0, never recomputed) so a null is distinguishable from a zero cost? [Clarity, Spec §FR-012 / data-model §C7, C8] <!-- Evaluator: Resolved — FR-036 (usd:null = unpriced/unknown, never read as 0, never recomputed) + SC-024 -->
- [X] CHK020 Is the per-turn versus per-run token aggregation rule specified (per-turn = sample at turn close, per-run = latest cumulative) clearly enough to be unambiguous when a turn has no sample? [Completeness, data-model §Entity Table / FR-005] <!-- Evaluator: Resolved — FR-036 (per-turn = sample at turn close, per-run = latest cumulative; sample-less turn shows "no usage reported", not 0) -->
- [X] CHK021 Are the requirements consistent that token usage is display passthrough only (never recompute cost) across spec, plan, and data model, with cost authority unambiguously assigned to the E007 usage seam? [Consistency, Spec §FR-012 / data-model §C8 / plan §Integration Points] <!-- Evaluator: Covered by spec.md §FR-012 + data-model §C8 + plan §Integration Points (FR-005/012 → E007 usage seam; display passthrough, no recompute), reinforced by FR-036 -->
