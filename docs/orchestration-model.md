# Orchestration model — As-is → To-be

How the hive coordinates work: agents & their working directories, status/control, delegation, integration, and the shared task board. Each section gives the **current** (shipped) behavior; "Later" notes call out what is still deferred.

Cast: **God** (`Michael`, the orchestrator — a singleton) and **workers** (DeepSeek/Minimax "native" desks, or Claude PTY desks). The god runs on the native runtime when the fleet default is a non-Anthropic model.

---

## 1. Agents & workspaces

- Every agent is created with one working directory (`cwd`), chosen in the Add-Agent dialog. **File access is two-axis (read wide, write narrow):** a desk may **READ** its own `cwd` *plus every project repo the fleet works in (registered repos, every desk's workspace, worktrees, the god workspace) + the whole hive home* (`<harnessHome>` — its own `memory.md`/`inbox`, `board.md`, `tasks.json`, and peers' dirs), so it can compare versions, read a peer's branch, or read its inbox. It may **WRITE** (`write_file`/`edit_file`) inside its own `cwd` (project code — gated by a code-editing role, see §5) **and** inside its own hive folder `<harnessHome>/hive/agents/<id>/` (`memory.md`, `inbox`, scratch — *ungated*, memory is everyone's). It may not write elsewhere; the shared `tasks.json`/`registry.json` change only through the hive tools (single-committer), so direct edits can't race the kanban. `bash` stays `cwd`-only + role-gated.
- **Who gets a worktree:** only code **AUTHORS** — `worker` / `planner` / `qc` — get their own **git worktree** (one per desk, off the latest trunk). The **integrator** and **reviewer** do NOT isolate: the integrator merges branches into the base/trunk host-side (`hive_integrate`→`mergeBranch`) and the reviewer is read-only, so both run in the **base tree on the trunk** (the integration target). Isolation is automatic per role (no per-agent toggle). Use separate repos only for genuinely separate projects.
- **Branch per task.** A worker authors each card on its OWN branch — the deterministic `agent/<id>-<cardId>` recorded on the card's `branch` field — checked out fresh off the trunk inside its one worktree. So a finished card integrates on its own branch while the worker starts the next card on a new one (never two cards on one branch). The integrator merges exactly the card's branch and deletes it after a clean merge; the worker's per-desk worktree persists.
- **Integrator = gate + merge, not author.** It keeps `bash` (the test/merge gate) + `hive_integrate` but NOT `write_file`/`edit_file`; merges are host-side and **serialized per repo** (one base tree → no concurrent-merge race). On conflict the merge aborts and the card routes back to its **author**, who rebases/resolves on their own branch. Scale integration by running **one integrator per repo** (different repos = parallel trunks), not multiple per repo.
- **Worktrees persist.** On agent exit the worktree + its branch are **kept** (committed work survives for the god to integrate); review and bulk-delete stale ones in **Settings → Worktrees**. (They are no longer force-removed on exit.)
- **Build output is redirected off the worktree.** Heavy, churning, executable build trees (a Rust `target/`, …) are not left inside a desk's worktree (or the repo) — that bloats the worktrees and, on Windows, drags real-time **antivirus** into the build path (file locks → `Access is denied`/`being used by another process` build failures). Instead the host injects build-tool env vars into each desk's build (both the native-bash and Claude-PTY spawn paths) from a **user-editable, token-templated table** (`config.buildEnv`, default `CARGO_TARGET_DIR=${buildRoot}/cargo/${worktreeKey}`). Each value's tokens are expanded per desk — `${buildRoot}` (the one parent folder: `config.buildCacheDir`, else `<harnessHome>/build-cache`), `${worktreeKey}` (the per-working-tree subfolder `<basename>-<hash>`, one builder per dir so cargo's per-`target` lock never contends), plus `${cwd}`/`${agentId}`/`${harnessHome}`. Any resolved value under the root is auto-created. Edit both in **Settings** (the folder + the var table). Net: the user defines ONE parent folder, the per-tool/per-worktree structure is filled in automatically, and **excluding that single folder from antivirus** covers every desk; nothing builds into a worktree or the repo. Adding a tool (e.g. `SCCACHE_DIR=${buildRoot}/sccache/${worktreeKey}`) is one table row.
- The **god** runs in its own neutral **home workspace** — `config.godWorkspace`, else `<harnessHome>/workspace` — separate from both the hive bookkeeping (`registry.json`, `board.md`, `tasks.json`, `agents/<id>/memory.md`, inboxes) and any worker's repo. It is a neutral base, *not* where the projects live: the god **reads** the project repos/worktrees to decompose + review, and only **edits** if the operator gives it a `worker`/`integrator` role (off by default → it delegates; see §5).
- Caveat: `bash` runs in a real shell, so when a desk *has* bash (a worker/integrator) it can reach outside its `cwd` for writes. The write sandbox is therefore partial for edit-capable desks; a role-less desk (god/reviewer/assistant) has no bash at all.
- **Later:** "god spawns workers on demand" (auto-provision a team into a project); tightening the `bash` write sandbox for workers.

## 2. Status & control

- A native desk's `agent.status` is driven by its live event stream: a global subscription sets `turn-start → working`, `turn-end`/`stop → idle` (skipped while paused / god-stopped / breaker-armed). One `displayStatus(agent, paused, godDesired)` derivation feeds the badge, the strip card, and the transcript — **god-stopped → idle**, **paused → waiting**, **streaming → working**, else **idle** — so they never disagree.
- The transcript's "working…" spinner shows only while `pendingTurn && !paused && !stopped`.
- **Stop** kills the worker (a synthetic terminal `stop` settles the transcript) and keeps it down across reloads until **Start**. **Pause** denies tools + parks the desk (the wake/drain leave it alone). A stopped *worker* revives on the next delegation/message (revive-on-demand).

## 3. Delegation & escalation

- The god delegates with **`hive_send_message`** — the actual dispatch into a worker's inbox. (The Tasks tab's "assign" button just pre-fills a message *to the god*; all human dispatch routes through the god.) A worker is woken by the inbox-wake loop and its end-of-turn drain delivers the content.
- **Inbox is a command, not a file.** New messages are auto-inlined into a desk's next turn by the drain (surfaced exactly once via its `cursor.json`); a desk re-reads on demand with **`hive_read_inbox`**. Desks should NOT `list_dir`/`read_file` the raw `inbox/` (the drain no longer points there). Memory is likewise command-driven: **`hive_read_memory`** / **`write_memory`**.
- **Undeliverable mail surfaces (no silent drop).** `hive_send_message` still queues the message but, when the recipient can't act on it now, tells the sender so — *"'X' is archived/stopped/unknown — reassign or message 'god'."* (from the live roster's `running`/`archived`). A message to a truly unresolvable id (no such desk / no inbox) is **dead-lettered to the god** (loop-safe) + logged `drop:undeliverable`, so the god can reassign or restore. We do NOT auto-restart a stopped/archived desk (operator intent); a stale *task* on an inactive assignee is surfaced separately by the kanban orphan chip + "fix assignments".
- **`hive_list_agents`** gives the god a host-mediated roster (`id, name, role, archived, running, repo, branch`) so it picks the best **available** desk instead of delegating blind. The god's loop: read roster + board, **decompose** a request into slices, create one **task card per slice** assigned to a desk, `hive_send_message` each. It can split one task across desks, assign different tasks to different desks, and re-route when a desk is blocked.
- **Escalation (worker → god).** A worker raises a blocker, ambiguity, conflict, or sign-off request by `hive_send_message {to:'god', act:'request'|'query'}`; it routes to the god's inbox and wakes it. This is the right channel — the god owns decisions/conflicts; workers don't guess or block silently.

## 4. The task board (`tasks.json` → Tasks tab)

Messages move work; the board records it — a living, single-source-of-truth with a role protocol:
- Statuses: `todo | doing | blocked | review | integrate | done`.
- **`hive_update_task`** `{ id, status?, assignee?, title?, priority?, note?, blockedBy? }`, **role-enforced**:
  - **Worker** — may update only a card **assigned to itself**, and only to `doing` / `blocked` / `review` (submit for review). It may **not** advance past `review`, set `done`, or reassign.
  - **Reviewer** — on a card in `review` (even if not the assignee) may add a `note` and either **approve** it to `integrate` or **send it back** to `doing`. It may not merge or set `done`.
  - **Integrator** — advances `integrate` cards, sets **`done`**/reopen.
  - **God** — may update **any** card to **any** status, plus reassign and reprioritize.
- **Comments:** a `note` is recorded as an **attributed comment** `{ by, at, text }` on the card's thread (not a freeform `description` append), rendered on the kanban card and **embedded in the send-back ping** so the worker is handed the feedback directly.
- **Blocked-by:** a `blocked` card carries **`blockedBy`** — the task id(s) it's waiting on (set when marking it blocked; auto-cleared on unblock). The board shows it as a coral **"⛔ blocked by ＜title＞"** chip that jumps to the blocker. Distinct from `dependsOn` (planning-time ordering). Non-task blocks use a free-text `note` + a message to god.
- **Project + orphan triage:** a card carries **`project`** (the repo it belongs to), stamped from the assignee's repo when it's **assigned** (and re-stamped on a god reassign) — never on drift. The kanban flags a card with a coral **"⚠"** chip when its assignee no longer fits: **inactive** (archived/gone), **no edit role** (a `todo`/`doing`/`blocked` card on a desk holding neither worker nor integrator), or **off-project** (`repoFor(assignee) ≠ project`). The toolbar's **"fix assignments"** button (and a `Fix assignments` schedule template) dispatches the god to reassign each to a capable available desk, or **unassign** (→ `todo`) + flag when there's no fit or the assignee is inactive/lacks permission.
- **Ownership lanes** (no write races — the hive is single-committer, the convention keeps lanes clean):
  - **God owns** create, assign, and (with the role) **sign-off**.
  - **Workers own** progress on their own cards (up to `review`).
  - **Reviewers own** the `review` gate; 
  - **integrators own** the `integrate`→`done` merge + sign-off.
- **Validation loop**: a worker finishes its slice (**runs the tests**, records the result as a comment) → sets its card **`review`** → the project's **reviewer(s)** are auto-pinged, read it (read-only), confirm tests cover + pass, and either **approve** (→`integrate`) or **send it back** (→`doing`) → on `integrate` **one** project **integrator** is auto-pinged, **re-runs the suite as the merge gate**, merges the branch, and sets **`done`** (or sends it back). No worker self-declares done; "done" means tested.

```
todo ─(god assigns)─▶ doing ─(worker)─▶ review ─(reviewer approves)─▶ integrate ─(integrator merges)─▶ done
                        │                  │                              │
                        │                  └─(reviewer: back)─▶ doing     └─(integrator: back/reopen)─▶ doing
                        └─(worker: blocked + blockedBy)─▶ blocked
```
(reviewer + integrator default to the god, or dedicated desks holding those roles; pings are matched per project)

## 5. Roles: who writes, who reviews, who merges

Work moves through three **capability roles** (separate from the god/assistant *identity*) — each desk can hold any combination:
- **`worker`** — writes the code **and its tests**. Eligible for delegated implementation; the god assigns slices here. **Can edit code** (write_file/edit_file/bash).
- **`reviewer`** — reviews a `review` card and **comments only** — it is **read-only**: write_file/edit_file/bash are **denied**. It reads the branch, leaves a `hive_update_task` note, then **approves** (→`integrate`) or **sends back** (→`doing`). It never merges and never sets `done`.
- **`integrator`** — merges an `integrate` card's branch (`hive_integrate`) and **signs tasks off** (`done`). **Can edit code** — it runs the test suite as the merge gate and writes the code that resolves merge conflicts.

**Two role classes.** It's useful to group the roles by what they're allowed to touch:
- **Authors** = `worker` / `planner` / `qc` — they **write project files** (`roleCanWriteFiles`) and get an **isolated worktree** (`roleAuthorsCode`); workers/qc also run `bash`. These are the desks that produce code + spec artifacts.
- **Coordinators** = god / assistant / `reviewer` / `integrator` — they **read everything** but **author nothing**: `roleCanWriteFiles` is false for all of them. The reviewer/god/assistant have no `bash`; the **integrator keeps `bash`** only as its test/merge gate (the one necessary soft-write vector) and merges host-side via `hive_integrate` rather than editing the trunk.

**The code-editing gate (`canEditCode`) = `worker` OR `integrator`.** A desk holding neither (a pure reviewer, the assistant, or an orchestrator-only god) is **write-disabled** — `write_file`/`edit_file`/`bash` are denied; it comments and delegates. (It can still **read** any project — see §1's two-axis access — so a hands-off god/reviewer reads the code to orchestrate/review without being able to change it.) This is the **god's delegation lever**: the **god holds `integrator` + `reviewer` by default** (so it merges out of the box), but because *both* worker and integrator grant editing, a god that should only orchestrate must have **both turned off** (leave `reviewer`) — then it physically cannot implement and must delegate. (The floor-roster role control shows this hint on the god.) Give the god the `worker` role to let it implement directly (solo mode).

Assign roles in **Add-Agent** (Worker / Reviewer / Integrator checkboxes) or per-desk via the desk's **gear → Desk options** modal. They persist in the registry; the **capability gate applies immediately** (read live), and changing a role **auto-restarts that desk** (~1s, debounced) so its role prompt re-injects — no app restart. A desk can hold any mix of worker/reviewer/integrator, or none.

Integration itself never hand-edits a repo (except to settle a conflict) — it uses one governed, registered-repo-scoped tool:
- **`hive_integrate { repo, branch, apply? }`** (allowed only with the **integrator** role): `apply` omitted/false **previews** (commits + diffstat vs base); `apply:true` **merges** into the repo's base branch. A **conflict aborts cleanly** and is reported, so the integrator either resolves it (conflict-only edits) or routes the work back to the author. Get each desk's `repo` + `branch` from `hive_list_agents`.
- Flow: worker tests + commits + sets card `review` → **reviewer** (auto-pinged) reads it and approves to `integrate` (or sends back) → **integrator** (auto-pinged) runs the suite, `hive_integrate` (preview) → `apply:true` → `hive_update_task done`; conflicts or red tests sent back. The god **delegates** review/integration for roles it doesn't hold.
- **Per-project routing:** the `→review` ping goes to **all** project reviewers (parallel review is fine — single-committer means only the first advance lands); the `→integrate` ping goes to **one** deterministic integrator (so two integrators don't double-merge). Both match the role-holder(s) **for the task's project** (via the assignee's repo — an isolated desk matches its worktree's *origin* repo), falling back to any holder, then **the god** (the standing fallback when no dedicated holder exists — it holds both roles by default and, as `isGod`, can advance any card).
- **Testing** lives in the pipeline, not a role: the **worker** runs the build/tests before `review` ("done" = tested), the **reviewer** verifies tests exist + cover + are green (read-only — it can't re-run), and the **integrator** re-runs the full suite as the **merge gate** before `apply`. A dedicated `tester` role can be added later if independent test authoring is wanted.
- Worktrees persist (§1) and a desk **reattaches** to its existing worktree on restart (so a role-toggle auto-restart never drops it into the shared tree); a workspace change to a different repo isolates at a repo-discriminated path, leaving the old worktree registered in its old repo. Dedicated reviewer + integrator agents are first-class (assign the role).

## 6. Spec-driven mode (SDDP) — an optional, gated lifecycle

A **per-floor toggle** (Settings → "Spec-driven mode (SDDP)") swaps the freeform decompose→code→review→merge flow for the **Spec-Driven Development** lifecycle. When **off**, everything in §1–§5 is unchanged (byte-for-byte). When **on**, the floor runs work **per feature** through a strict, gated lifecycle with artifacts in `specs/<feature>/`:

```
Specify (spec.md) → Clarify → Plan (plan.md) → Tasks (tasks.md) → Implement → QC (.qc-passed) → Integrate
```

**Why it's ported as prompts + tools, not "run SDDP":** the `/sddp-*` skills and `sddp-*` sub-agents are **Claude Code CLI** features (slash-commands + the Task tool). A **native** (DeepSeek/Minimax) desk runs the app's own loop + in-house toolkit — no slash, no Task tool — so it can't invoke them. The SDDP *methodology* (phases, the `specs/<feature>/` artifacts, the task grammar, the `.completed`/`.qc-passed` gates) is delivered to every desk as **role prompts**, and the lifecycle is **machine-enforced** by host tools so a forgetful model still can't skip a phase. A **Claude** desk *additionally* gets a note that it MAY run the real `/sddp-*` skills (hybrid bonus).

**Two new roles** (shown only in SDDP mode, alongside worker/reviewer/integrator):
- **`planner`** — authors a feature's `spec.md` → clarifications → `plan.md` → `tasks.md` (Specify→Clarify→Plan→Tasks). Does not implement.
- **`qc`** — runs the automated QC phase: build/tests/lint/security + verifies each user story / `SC-###` against the code, writes `qc-report.md`, then creates the `.qc-passed` marker or files `[BUG]` tasks back to workers.

Both can write (planner writes artifacts; qc runs the suite via bash), so `canEditCode` = `worker || integrator || planner || qc`; their narrower scope is prompt-enforced (like the integrator's conflict-only edits).

**Lifecycle → role mapping.** **god** drives the lifecycle and enforces the gates (assigns each phase to the right role-desk; orchestrates, never authors/implements) → **planner** writes the artifacts → **reviewer** owns two read-only gates (the **spec/plan** review, then the **code** review) → **worker** implements `tasks.md` → **qc** runs the QC phase → **integrator** merges only after `.qc-passed`. Multi-agent pays off by **parallelizing Implement** across workers and running a **feature pipeline** (one feature in Plan while another is in QC); a single feature's sequential spec→plan→tasks is *not* fanned out.

**Machine-enforced gates (the key lever for native desks).** The host reads the feature's **real on-disk markers**, so the lifecycle is reliable regardless of model discipline:
- **`hive_feature_status { feature }`** reports a feature's current phase + next unmet gate from `specs/<feature>/` (`spec.md`, `## Clarifications`, `plan.md`, `tasks.md`, `.completed`, `.qc-passed`). Desks read the truth instead of remembering it. The pure `featurePhase()` helper backs both this tool and the kanban banner.
- **Hard gates in `hive_update_task`** (SDDP mode + a card carrying a `feature` only): no `doing` without `tasks.md`; no `integrate`/`done` without `.qc-passed`. Applies to **everyone** (god included — the markers are the single source of truth). **Fails open** when the host can resolve no status (no `specs/<feature>/` yet), so a missing scan never deadlocks the board — only a *known-missing* marker blocks the move.
- A card carries an optional **`feature`** (its `specs/<feature>/` folder), stamped on `hive_add_task`/`hive_update_task` (or via the Add-Task form's feature field in SDDP mode). The host scans `<task.project>/specs/<feature>/`; `feature` is sanitized to a single path segment (no traversal).

**Shared `specs/` across worktrees.** `specs/<feature>/` is **shared coordination state**, not per-desk code — but desks working one repo run in **isolated git worktrees** (§1), which would silo each desk's writes to its own branch (a planner's `tasks.md` invisible to the gate-scan + workers). So in SDDP mode the toolkit **anchors the `specs/` subtree to the base repo**: any `read_file`/`write_file`/`edit_file`/`list_dir`/`grep` path under `specs/` is remapped to `<repoFor(desk)>/specs/…` (the worktree's origin, or the cwd for a non-isolated desk — a no-op). So every desk reads+writes **one** copy of the artifacts regardless of worktree, while CODE stays on each worker's branch. Still role-gated (a read-only reviewer can't author artifacts); inactive when SDDP is off. *Caveat:* concurrent direct edits to a shared `specs/` file (e.g. two workers ticking `tasks.md`) are last-write-wins — not single-committer like `tasks.json`.

**Phase auto-routing (planner + qc).** Like the reviewer/integrator pings (§4), the two new phases get a structural kickoff from the task notifier, gated on the feature's real markers and with **no god fallback** (per operator: no role-holder ⇒ nobody does it — the god is a delegator that can't author specs or run QC):
- **Planner** — a feature with cards but **no `tasks.md`** pings a `planner` desk to author spec→plan→tasks (deduped once per feature; re-tried on a later board write so a planner added later still gets pinged).
- **QC** — a feature card entering `integrate` **without `.qc-passed`** pings a `qc` desk to run the QC phase *instead of* the integrator; the integrate gate keeps the card from merging until `.qc-passed` appears, after which the integrator picks it up on its next scan. A non-feature card (or a `.qc-passed` feature) pings the integrator as before. A missing planner/qc handler is logged (`no-handler`), not silently dropped.

**Feature phase tracker (kanban).** In SDDP mode the Tasks tab keeps the six columns and adds a **banner per feature** above them: the phase ladder (Specify → … → Integrate) with the current phase highlighted and completed phases ticked, plus a "clarified" indicator and card count, polled from `hive:featureStatus`. A feature with no `specs/<feature>/` yet shows "not started".

**Native sub-agent runtime (`spawn_subagent`) — the Task-tool replica.** sddp27's power is ~18 single-responsibility **sub-agents** the `/sddp-*` skills delegate to via Claude's Task tool. A native (DeepSeek) desk has no Task tool, so the host gives it `spawn_subagent { name, input }`: MAIN forks an **ephemeral one-shot worker** whose system prompt IS the named specialist's prompt, runs it for a single turn on the caller's input, captures its final text, and tears the process down. Two layers, not competing: a hive **role** is *who owns the phase on the floor*; a sub-agent is *an ephemeral specialist the owner spawns inside that phase*. The registry (`coordination/subAgents.ts`) carries the native adaptations of all ~18 (`spec-validator`, `database-administrator`, `api-designer`, `adr-author`, `wbs-generator`, `qc-auditor`, `story-verifier`, `developer`, …); each declares its `roles` (read-only validators → none; spec authors → `planner`; the developer → `worker`). Guardrails (every spawn is a full LLM loop): the child runs **caller-scoped** (its tools resolve cwd/repo/roles to the caller, so the `specs/` redirect + worktree are correct for free), with a **deny-list** (no nesting, no `hive_integrate`, no board mutation), **low turn/hop caps + a turn budget**, a **wall-clock timeout**, and a **concurrency cap**. The child's **token cost rolls up to the caller**; the sub-run is visible as the caller's `spawn_subagent` tool call + result. Only the orchestrating roles (planner/qc/worker) are advertised the tool (`roleCanSpawnSubagents`). The model is the caller's, unless `sddpSubAgentModel` overrides it to a same-provider model. A **Claude** desk skips all this — it runs the real `/sddp-*` skills. **What drives it:** the SDDP role prompts (`src/main/sddpPrompts.ts`) explicitly instruct the planner/qc/worker to `spawn_subagent` their specialists per phase and `advanceMilestone` after each artifact — without that, the runtime would sit advertised-but-unused. A regression test (`sddpPrompts.test.ts`) asserts the prompts keep naming the tool + the specialists.

**Milestone pipeline on the feature epic card.** The god creates **one EPIC card per feature** — `hive_add_task { feature, epic:true }` — which seeds an ordered **milestone checklist** (`HiveTask.milestones[]`, from `defaultMilestones()`/`SDDP_MILESTONE_TEMPLATE`): spec → clarify → research → data-model → contracts → adrs → plan → checklist → tasks → implement → qc. (The epic is exempt from the implement-only "no `doing` without tasks.md" gate — it's worked during planning and tracks progress via its milestones.) The owner advances it with `hive_update_task { advanceMilestone }`, which is **hard-gated on the milestone's real artifact** under `specs/<feature>/` (`featureArtifactExists`) — e.g. `data-model` needs `data-model.md`, `tasks` needs `tasks.md`. **Optional** steps (clarify/research/data-model/contracts/adrs/checklist) may advance **without** their artifact (a feature with no API/data-model isn't stranded); the **required** backbone (spec/plan/tasks/implement/qc) needs its artifact. Advancing is **decoupled from spawning** — the milestone names the `subAgent` to spawn, but `advanceMilestone` only records + gates (the owner spawns the specialist separately). The board renders the checklist as a read-only pill row under the phase banner.

**`hive_import_tasks { feature, assignee? }` — Tasks → cards.** Once the Tasks milestone is ready (`tasks.md` exists), the owner calls this to turn the plan into work in one shot: the host parses the feature's `- [ ] T###` lines (stripping the `[P]`/`[US#]`/`{FR-###}`/`[after:…]` annotations to the description), and the executor creates one feature-tagged implement card per task (status `todo`, optionally all assigned to one worker, else unassigned for the god to route).

**End-to-end (a native SDDP feature):** the **god** creates the epic card (`hive_add_task {epic:true}`) → assigns Plan to a **planner**, which `spawn_subagent`s `requirements-scanner` (clarify), `database-administrator`→`data-model.md`, `api-designer`→`contracts/`, `adr-author`→`adrs/`, `wbs-generator`→`tasks.md` (spawning only what the feature needs), running `spec-validator` to check the spec, and `advanceMilestone`-ing each as its artifact lands → a **reviewer** approves the spec/plan → the god runs `hive_import_tasks` → **workers** implement the resulting cards (optionally delegating a slice to the `developer` sub-agent) → a **qc** desk `spawn_subagent`s `qc-auditor` + `story-verifier`, writes `qc-report.md` + `.qc-passed`, and advances the `qc` milestone → an **integrator** merges. The epic's pill row on the board tracks the whole arc; each sub-agent run shows as the owner's `spawn_subagent` tool call with its cost rolled up to the owner.

**Host-driven SDDP engine (`sddpPipeline.ts`) — the deterministic alternative to "trust the desk."** The model-driven flow above relies on the planner desk *choosing* to spawn its specialists. The host engine makes the mechanical phases deterministic instead: the feature epic card's milestone checklist is the *program*, and the engine is the *interpreter*. On every board change the hive fires a per-feature trigger (`setPipelineTrigger`, fire-and-forget); the engine finds the epic, validates it has a **usable native owner desk** (a spawned non-Claude desk with a model — it runs the specialists *as* that owner, inheriting creds + holding the feature card), and for the active **host-driven** milestone (`milestoneDriver` → `spec`/`research`/`data-model`/`contracts`/`adrs`/`plan`/`checklist`/`tasks`) it runs that step's sub-agent, gates on the real artifact (`featureArtifactExists`), advances the milestone (`hive.advanceMilestone` → re-triggers → chains to the next), and **skips** an optional step that produces nothing. `spec` is authored by `spec-author` from the epic's `description` (the feature request). The **`clarify`** step is **human-gated** (see the Human-Gates Registry): the engine relays `requirements-scanner`'s questions and PAUSES, unless `sddpAutopilot` is on (then `spec-author` resolves them with documented defaults). The remaining steps (`implement`, `qc`) are **distributed** — the engine FEEDS + TRACKS them rather than running them: at `implement` it **seeds the implement cards** from `tasks.md` once (deterministic; `seedImplementCards`), so the work exists and the god just assigns them to workers; then it **advances the `implement`/`qc` pills when the real markers land** (`.completed` / `.qc-passed`), which the existing distributed flow produces (workers → the notifier-pinged **qc desk** that writes `qc-report.md` + `.qc-passed` → the **integrator** merges). (Host-DRIVEN QC — a `qc-auditor` sub-agent creating `.qc-passed` — is deferred: it needs a QC-integration worktree to avoid the `.qc-passed`-gates-`integrate` deadlock.) In the Human-Gates Registry, **#3 (spec/plan review) is not an engine gate** — the engine advances on artifacts — and **#4/#5 (code review, integrate)** are the existing per-card board flow on the seeded implement cards. No usable owner, or a required artifact that never lands, **escalates** to the god/operator (de-duped). **Templates are data the engine supplies** (`sddpTemplates.ts`, `templateForStep`): the engine prepends the step's structure to the sub-agent input ("author into THIS structure") rather than baking it into the prompt — so `plan-author` assembles `plan.md` into sddp27's plan template, `wbs-generator` into the tasks template, etc. Guards: a debounced `schedule`, a per-`feature::step` in-flight lock, and never throwing into the write path. (Spec/clarify host-driving + implement/QC are later engine phases.)

**Per-step operator control + monitor (the milestone pills).** Each milestone carries a `control` (`auto` | `paused` | `stopped` | `manual`, default `auto`) the operator sets from its board pill (rides `tasks.json` → `hive:writeTasks`); the engine reads the active step's `control` first, every trigger: `paused` = don't run/advance (resumable); `stopped` = **abort the in-flight sub-agent** (kills the ephemeral worker via an `AbortSignal`) + hold; `manual` = the engine skips the run and advances when the step's artifact appears (a desk/human authored it — your "switch to manual"); back to `auto` resumes engine driving. The engine also keeps a live per-feature **status** (`running`/`waiting`/`paused`/`stopped`/`manual`/`blocked`) exposed via `pipeline:status`; the pills show it (⟳ running, … waiting, ⚠ blocked) next to the control buttons. **Auto-assign:** the engine assigns the **epic → a usable planner desk** (so it has an owner to run sub-agents as) and **round-robin-assigns the seeded implement cards → worker desks** — "driven AND assigned."

**Human-Gates Registry (what's human-in-the-loop, and how each goes auto).** SDDP has a small set of human checkpoints; the operator can flip them to automatic with **`sddpAutopilot`** (OFF by default — mirrors sddp27's AUTOPILOT). Tracked canonically here:

| # | Gate | Phase | Default (human in loop) | Autopilot (auto) | Status |
|---|------|-------|-------------------------|------------------|--------|
| 1 | Feature request | Specify input | operator provides the *what* (epic card `description`) | inherent input — could later be sourced from a PRD/epic doc | input |
| 2 | **Clarify answers** | Clarify | engine runs `requirements-scanner`, relays its questions (`needs_human`), PAUSES; operator answers + advances `clarify` | `spec-author` resolves each `[NEEDS CLARIFICATION]` with a documented default → auto-advance | **done (P3)** |
| 3 | Spec/Plan review | after Plan | a reviewer approves `spec.md`/`plan.md` | `spec-validator` + `policy-auditor` pass → proceed | P4+ |
| 4 | Code review | after each Implement slice | a reviewer approves to integrate/QC | `story-verifier` + the worker's green tests | P4+ |
| 5 | Integrate sign-off | Integrate | an integrator desk merges (operator may watch) | auto-merge once `.qc-passed`; optional operator-confirm | P4+ |
| 6 | QC tool install | QC | — | already auto (`qc-auditor` marks SKIPPED, never installs) | done |

The host engine itself only owns gate **#2** today (the rest are the model-driven flow's review checkpoints — the engine advances on artifacts, not approvals); #3–#5 attach to the same `sddpAutopilot` flag as those phases land.

**Applying mode changes — "restart required".** SDDP mode (and any setting baked into a desk at spawn — `autoMode`, `terminalTheme`) only takes effect when a desk **respawns**: `workerEnv`/`ensureAgent` read the config once at spawn, and "resume from the floor" is an un-pause, not a respawn. So each desk is stamped at spawn with a snapshot of those values (`Agent.spawnSig`, restartSig.ts); when one differs from the live config the desk is **running with outdated settings** and is surfaced three ways — a count badge on the title-bar gear, a per-desk **⟳** chip on the agent card (click restarts that desk), and a Settings banner listing the changed settings with a **"restart affected desks"** button. Toggling a value back to its original auto-clears the flag; a desk spawned after the change (or restarted) is never flagged. Restart is **on demand** — toggling never silently interrupts a busy desk.

**Deferred:** shipped spec/plan/tasks/qc templates; per-project/per-agent mode; a finer capability gate so planner/qc can't touch source at all; a richer child-run viewer (the sub-run is currently visible via the `spawn_subagent` tool call + cost rollup, not a dedicated transcript).
